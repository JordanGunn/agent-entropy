# 4.2 Trajectory

*The time-bearing context of the work: where it has been, what was known and decided, and where it must still be able to go.*

The most unsettling complaints from the opening section are not about what the agent was asked to do, but about how the work reached its present state and where it is still allowed to go. It cleaned up a module and left it bigger, more entangled, and less legible than before. It built an abstraction the project did not ask for, foreclosing a path no one meant to close. None of these is a failure of the goal: the goal was understood. Each is a failure of **trajectory**, the time-bearing context the agent should have brought to the work and did not have.

Trajectory has two tenses: **provenance**, the resolved delta that produced the present (how the work got here, so the agent does not undo a change it cannot see was deliberate), and **horizon**, the deltas the work must still be allowed to produce next (where it is going, so it does not close a door the project will need open). The agent brings neither by default. When the record is not supplied, it does not leave it blank; it fills it by invention, calibrated to the wrong project. The accumulated cost is the **Entropy of Trajectory**, the counterpart at the level of time to the Entropy of Comprehension (the comprehension section). Provenance and horizon are not two pillars but two ways one record of movement comes apart.

## Provenance: the resolved delta

You return to a piece of code written three months ago (by you, by the agent, by some collaboration whose distribution of effort is no longer recoverable) and ask the agent to clean it up. By the end of the session the affected area is bigger, more entangled, and less legible than when you started. Nothing was deleted; everything was preserved. The thing that was wrong is still there, now welded to the thing that was supposed to fix it. Some of that is the model, some the prompt; most is structural. The agent was asked to remediate a codebase whose decisions it cannot read.

> Provenance is not the past, and it is not memory.
> It is the meaning of the difference between the context now and an earlier one: what changed, what was superseded, what became known, what became false, what is still unknown, and what future decisions now inherit.
> The code preserves the result. It does not preserve the reasoning, or the road not taken.

This is not the supply-chain, build-attestation, or data-lineage senses of *provenance*, and it is not a decision log. It is the resolved meaning of a context delta. Write `C` for the context, `C[i]` the active state now, `C[j]` an earlier one.

```text
ΔC[i,j] = diff(C[j], C[i])     the contextual diff: earlier state C[j] → current state C[i]
P[i,j]  = A(ΔC[i,j])           provenance: the agent's resolved reading of that diff
C⁺[i,j] = C[i] + P[i,j]        the present context, enriched by the resolved delta
```

Provenance is `P[i,j]`, not `ΔC[i,j]`: not the raw difference but the agent's interpretation of it, the same `A( )` that infers a goal from a context, run over a diff. Precisely, `P = A(ΔC)`: the delta, resolved.

This is why ordinary memory does not solve the problem. The agent does not need a pile of retained statements; it needs the present context plus a resolved delta: `C⁺ = C + P`. Remembering is easy: a system can store every statement ever made. The hard part is knowing what to invalidate, supersede, scope, or forget, and that a memory does not do. A stored fact can be partly true and partly stale, and the agent overfits to the true-looking part while silently acting on the stale part, because nothing in a flat memory marks which part still applies. Provenance marks it: it preserves movement, not facts.

### Documentation fails quietly

The canonical attempt to preserve provenance is documentation: design docs, READMEs, ADRs, `CLAUDE.md` files, comments. Each writes the why down somewhere it can be retrieved, and each rots silently. Code at least fails visibly when it diverges from reality; a markdown file that no longer reflects the team's decisions produces nothing, sitting there authoritative and wrong, waiting to be read. An agent onboarding reads a `CLAUDE.md` as ground truth, with no memory of the refactors since it was written that quietly reversed a decision in a way never dramatic enough to prompt an update. The delta framing names the failure exactly: a rotted document is an old context state `C[j]` wearing the badge of the current one, read as `C[i]` because nothing computed the difference. What derails the task is the unresolved delta: the paragraph that should have been marked superseded and was not.

Parnas saw the mechanism in 1994. Software ages *(Parnas, 1994)*: not because hardware fails, but because the understanding that produced the software slowly decouples from it. The same applies one layer above code, to the artifacts meant to preserve the design concept. What makes it compounding is the subtlety of the drift: five decisions, each slightly updated, none quite inconsistent enough to trigger an alert, accumulate into a document plausible at every sentence and wrong in aggregate.

### Fusion is the conservative response to opacity

When the gap reaches the threshold at which the codebase becomes opaque, the failure mode changes shape: it stops being gradual and becomes catastrophic, and the catastrophe arrives during the activity that was supposed to fix the problem, remediation. Asked to refactor a module or untangle a dependency, the agent encounters artifacts whose provenance is invisible. It cannot distinguish a deliberate choice from a workaround, cannot tell which assumptions were load-bearing. It holds `C[i]`, the code as it stands, but cannot compute `P`. Unable to tell what was superseded, it supersedes nothing.

Fusion is the conservative response to opacity. The agent removes nothing and adds new code alongside. Each fusion increases surface area without reducing legacy: old assumptions become embedded in the new architecture, new patterns entangled with old anti-patterns. The output compiles and passes tests, and simultaneously destroys the legibility of every decision that preceded it. The choice to fuse rather than replace is the sycophancy mechanism from the four-entropies section, applied to the codebase as the source of agreement: removal asserts that something was wrong, addition only that something else is needed, and the agent takes the lower-disagreement option.

This is **provenance collapse**: the irreversible loss of decision lineage, producing a state in which neither developer nor agent can reliably determine what was intentional, what was accidental, and what was the artifact of a remediation that fused both. The record of what the signal was supposed to be is destroyed. It is the smell that defines the point of no return.

Fusion has a second root, taken up in the agency section: even when provenance is present and the old state is visibly wrong, the agent may lack the *authority* to declare it so. Removal is the higher-authority act, and an agent unsure of its remit defaults to the lower one. Missing provenance and missing authority drive the same conservative fusion from different directions.

That decision lineage must be preserved as an artifact distinct from the code is not new. Cunningham named technical debt (financial and intentional, where provenance rot is decay no one agreed to); Gall, Hajek & Jazayeri and Tornhill built the change-coupling instrument that inverts into a decay signal; Nygard named Architectural Decision Records, admired and inconsistently maintained, because maintenance is socially expensive and structurally optional. Each assumed a human who reads the documentation before changing the code and carries lineage between sessions. The agent does none of this, so the bar for the artifact rises substantially.

The intervention is to stop treating provenance as documentation and treat it as an event log: a structured record of intent events, auto-recorded by the agent's lifecycle, sealed at completion, and attached to the commit that landed the change. Each event captures the what and the why (scope, rationale, assumptions in force, decisions made, alternatives rejected, what is out of scope) in a template that forces the why field to exist. The log is queryable (the agent retrieves the intent that produced a piece of code before changing it) and drift-detectable (a sealed intent whose code was rewritten without a new intent is the same change-coupling signal on structured artifacts). The ADR was one the team agreed to maintain; the intent log is one the system produces. Teams forget; systems do not.

## Horizon: the future

A developer making a local change carries a rough picture of where the project is going, and that picture does two things at once. It quietly vetoes locally-reasonable choices that would make the future harder (a boundary that will block an intended integration, a shortcut welded into the seam a future capability will need) and it quietly permits locally-unjustified ones the future will reward (the boundary drawn a little cleaner than today demands, the seam left where an intended capability will land). The agent carries no such picture. Optimising for the present request, it does both wrongs: it closes doors it does not know the project will need open, and it refuses to leave open the doors it cannot see a reason for, suppressing as premature the very investment the horizon would license. Horizon governs creation: it is the permission to keep a door open that a context-blind agent reads as YAGNI and declines.

The foreclosing case is a future-hostile decision: locally reasonable, globally costly, and invisible at the moment it is made because nothing in the current task reveals it. It surfaces only later, when the foreclosed path is needed and found welded shut. But the permission the horizon grants is exactly as dangerous when misread, and naming why is the core of this component. Future vision injected as instruction becomes premature implementation: an agent told the project will eventually support multiple backends will build the abstraction now, before it is needed, against the explicit wisdom of *You Aren't Gonna Need It*. So the permission carries a sharp boundary: keep the door open, do not walk through it. Supply the future at a weight low enough to shape which doors stay open without becoming a task to complete. Permission to leave a seam is not permission to build the room behind it.

The components differ in standing: comprehension is executable now, provenance is lineage to verify against, and horizon is direction only, non-executable unless explicitly promoted to intent.

Horizon's prior art is two traditions that look opposed. Parnas's design for change is the foundation: anticipate the changes a system is likely to face and hide each behind a boundary, a method that presupposes the very artifact Horizon is meant to be. YAGNI (Beck) is the counter-pressure: do not build for an imagined future, because most never arrive and the speculative generality is pure cost. Baldwin & Clark reconcile them in the language of real options: modularity has value precisely because it keeps options open without exercising them. The constraint follows: keep the path open (Parnas) without building it (YAGNI), because an unexercised open path has value in itself (real options), achievable only if the future is held at advisory weight. Parnas's method assumed an architect who held the roadmap in their head, free because the future lived in the same mind writing the code. The agent holds no roadmap, and being told one as ordinary instruction makes it build the future today.

The intervention is a small, explicitly non-executable statement of direction: a north star, likely future capabilities marked not current scope, non-goals for now, design sensitivities, and promotion criteria that say what would turn a horizon item into actual intent. Each item carries a last-revalidated timestamp, so a horizon not checked against reality grows weaker, not silently more binding, the inverse of how prose roadmaps rot. This component is the most forward-looking in the paper, and its instrument the most speculative, for a reason worth stating plainly: a future-hostile decision can only be confirmed in hindsight, once the foreclosed path is actually needed. At that moment the only thing to check against is a declared horizon, so the artifact is both the intervention and the measurement surface. The diagnosis is sound; the instrument is a hypothesis.

The two tenses complete the trajectory, symmetric about the present. The agent that holds neither assumes both, toward the average of its training distribution. Like the Entropy of Comprehension, the Entropy of Trajectory is meant to be measured: its wake is read in the artifact's quality (the quality section). Each is missing on its own terms; each must be supplied on its own terms.

---

The model did not get worse. The trajectory it has to assume got harder to supply. Provenance and horizon were never written down before, because the people deciding already knew them. Those people are no longer the ones deciding. The interventions in this section are not about constraining the model. They are about capturing the why the model cannot reconstruct and stating the direction it must see but must not build, so that remediation resolves the delta instead of fusing it, and today's choices stop foreclosing tomorrow's. Precision at the point the trajectory is set is cheaper than precision at the point the damage is found, and the difference compounds across every commit that inherits it.
