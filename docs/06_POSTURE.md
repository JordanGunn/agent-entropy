# V. The Posture Gap

*The stance a decision is made from — where the project has been, and where it is going — and the regime that says how much it all matters.*

The complaints from the opening section arrive in more than one shape, and the most unsettling of them are not about what the agent was asked to do. They are about the stance it took while doing it. It cleaned up a module and left it bigger, more entangled, and less legible than before. It warned about a migration that cannot matter yet. It built an abstraction the project did not ask for. None of these is a failure of the goal. The goal was understood. Each is a failure of **posture** — the decision stance the agent should have brought to the work and did not have.

The whole-context section named posture as the lineage the present rests on — its two tenses are **provenance** (the past the code already embeds) and **horizon** (the future it is trying to keep room for). Two senses a developer brings to every change without thinking about it: where the project has been (so they do not destroy a decision they cannot see), and where the project is going (so they do not close a door it will need open). A third sense — how much any of it matters — used to be counted here too, as scale; this section treats it under its own name, **stakes**, because it turned out to be not a tense of the work but the regime the work is read under. The agent brings none of them by default — and the failure they share is the one that makes posture dangerous to omit. When a posture component is not declared, the agent does not leave it blank. It fills it by invention, confidently, and calibrates the invention to the wrong project.

The accumulated cost of those inventions — lineage the agent cannot see, directions it forecloses — is the **Entropy of Posture**: the degradation of the decision stance, the posture-level counterpart to the Entropy of Interaction (the intent-gap section). Naming it at the level of the stance, not its parts, is deliberate — provenance and horizon are not two separate pillars but two ways one stance comes apart. (Miscalibrated stakes belongs to the same family of harm but is not part of this decay: it is a regime set wrong, not a lineage that rots, and it is treated on its own terms below.)

This section is posture in full — provenance and horizon, the way each fails when it is missing, the prior art that assumed a human would carry it, and the artifact that has to carry it now — and then the stakes regime the old framing mistook for a third posture component.

## Provenance: the past

You return to a piece of code written three months ago — by you, by the agent, by some collaboration whose distribution of effort is no longer recoverable. You ask the agent to clean it up. It tries. By the end of the session the affected area is bigger, more entangled, and less legible than when you started. Nothing was deleted. Everything was preserved. The thing that was wrong is still there, now welded to the thing that was supposed to fix it.

Some of that is the model. Some is the prompt. Most is a structural property of the situation: the agent was asked to remediate a codebase whose decisions it cannot read.

> Provenance is not the code.
> Provenance is the chain of intent and assumption that produced the code.
> The code preserves the result. It does not preserve the reasoning.

A note on the term. Provenance here refers to the lineage of architectural decisions — not the supply-chain, build-attestation, or data-lineage senses used in security tooling and scientific computing. What is at stake is the chain of intent and assumption that produced the current code state, and what is lost is the ability to reconstruct that chain after the fact.

### The code does not carry it

Every line was written under a set of assumptions alive at the time it was written. Whoever wrote `read_pdf()` knew why it was named that way, what it was expected to do, what it was explicitly not expected to do, and what would change if requirements shifted. That knowledge was alive at the moment of the decision. It is not preserved in the code. It is rarely preserved in the commit message. It dissipates.

The dissipation is gradual, invisible, and structural. No one notices the moment the assumption behind a function stops being remembered, because no one is asked the relevant question on the day after it is forgotten. The question is asked later — months later, by a maintainer or an agent trying to extend or remove the function — and at that point the answer is gone. In a traditional context this is manageable: humans reading old code carry enough contextual awareness to compensate. They ask the original author, check the design archive, reconstruct intent from having been in the room. The documentation is incomplete, but the humans around it close the gap. In an agentic context, this compensation does not exist.

### Documentation fails quietly

The canonical attempt to preserve provenance is documentation: design docs, READMEs, ADRs, `CLAUDE.md` files, comments. Each is an attempt to write the why down somewhere it can be retrieved. Each rots, and rots silently.

Documentation does not break the way code breaks. Code at least fails visibly when it diverges from reality. A markdown file that no longer reflects the team's decisions produces nothing — it simply sits there, authoritative and wrong, waiting to be read. An agent onboarding to a codebase reads a `CLAUDE.md` the same way it reads anything else: as ground truth. It has no memory of the three refactors since that file was written. It cannot sense that the package structure in section two no longer exists, or that the decision in section four was reversed, then partially reversed again, in a way never quite dramatic enough to prompt an update. It reads, infers, and acts — on a specification that has been quietly wrong for months.

David Parnas saw the mechanism in 1994. Software ages *(Parnas, D.L., 1994)*: not because hardware fails, but because the understanding that produced the software slowly decouples from the software itself. Parnas was writing about code. The same observation applies one layer above it, to the artifacts meant to preserve the design concept in the first place. What makes it compounding is the subtlety of the drift. A single superseded decision is easy to catch. Five decisions, each slightly updated, each not quite inconsistent enough to trigger an alert, accumulate into a document that is plausible at every sentence and wrong in aggregate.

### The decoupling signal

Adam Tornhill's behavioural code analysis offers an apparatus for measuring this decay, though it must be inverted to apply here. Tornhill studied **change coupling** — files that consistently change together, revealing logical dependencies static analysis cannot see. The signal in his work is the presence of co-change. The signal here is its absence: source files that change without the documentation supposed to describe them. Documentation rot is a decoupling phenomenon — a silent failure of co-change between artifacts the team's mental model treats as linked. The same instrument that reveals hidden coupling can, run in the negative, reveal hidden divergence *(Gall, Hajek & Jazayeri, 1998; Tornhill, A., 2015)*.

This is not a discipline problem. Teams that maintain perfect documentation are not failing at discipline when their `CLAUDE.md` rots; they are using a representation designed for human readers, with all the compensating mechanisms humans bring, applied to a system that has none of them. The format is wrong for the audience, and the decay was guaranteed from the start.

### Fusion is the conservative response to opacity

When the gap reaches the threshold at which the codebase becomes opaque, the failure mode changes shape. It stops being gradual and becomes catastrophic, and the catastrophe arrives during the activity that was supposed to fix the problem: remediation.

The mechanism is precise. Asked to remediate — to correct an architectural decision, refactor a module, untangle a dependency — the agent encounters artifacts whose provenance is invisible. It cannot distinguish a deliberate choice from a workaround. It cannot tell which assumptions were load-bearing. Faced with this opacity, it does the only safe thing available: it preserves what exists while incorporating what is new.

Fusion is the conservative response to opacity. The agent does not know what is safe to remove, so it removes nothing and adds new code alongside. Each fusion increases surface area without reducing legacy. Old assumptions become structurally embedded in the new architecture; new patterns become entangled with old anti-patterns. The output satisfies the immediate request — it compiles, it passes tests — and simultaneously destroys the legibility of every decision that preceded it. The choice to fuse rather than replace is the sycophancy mechanism from the three-entropies section, applied to the codebase as the source of agreement: removal asserts that something was wrong; addition asserts only that something else is needed, and the agent takes the lower-disagreement option.

This is **provenance collapse**: the irreversible loss of decision lineage from a codebase, producing a state in which neither developer nor agent can reliably determine what was intentional, what was accidental, and what was the artifact of a remediation that fused both. In information-theoretic terms it is the phase change within the gradual-decay story: the signal does not merely degrade; the record of what the signal was supposed to be is destroyed. It is the smell that defines the point of no return.

### The ceremonial reviewer

The standard response to all of this is the same one offered for every AI failure mode: the human is in the loop. Read the diff. Check the tests. Approve thoughtfully. The advice is universal, and almost no one follows it — not from moral failing, but from three structural pressures.

**Responsibility laundering.** Vendors market autonomy; users adopt the tool because it was marketed as autonomous; when something breaks, the response is "you should have reviewed more carefully." A closed loop with no accountable actor. Lisanne Bainbridge described it in *Ironies of Automation* (1983): humans are asked to supervise automated systems specifically because they cannot replicate the output, then blamed when supervision fails *(Bainbridge, L., 1983)*. Parasuraman and Riley (1997) catalogued the same across aviation, medicine, and industry — misuse, disuse, abuse *(Parasuraman, R. & Riley, V., 1997)*. Agentic tooling has rediscovered the failure mode without acknowledging the precedent.

**Negative pedagogy.** Every interaction updates the user's prior about whether vigilance is necessary — and the prior updates monotonically toward trust regardless of whether trust is warranted. Visible successes train the user that review is unnecessary. Invisible failures also train the user that review is unnecessary, because the user did not observe them. There is no feedback path that increases vigilance except a catastrophic, attributable failure — precisely the kind this paper argues is most likely to be hidden long enough to lose attribution. The human is not worn down by laziness. They are trained out of the loop by the tool itself.

**Economic incompatibility.** "Review the code carefully" is unfollowable in principle at the volume the tooling produces. If the agent generates eight hundred lines and twelve tests, careful review approaches the cost of writing it originally. The entire value proposition collapses if the recommended supervision is performed. The advice is therefore not advice — it is an unfalsifiable defence: anyone diligent enough to follow it is, by definition, not getting the advertised benefit.

What is left is **ceremonial review**. The human still presses approve, still merges the PR — but none of these actions carry information anymore. The form of supervision is preserved; the function is gone. The clearest evidence is the shape of the ecosystem itself: the most active community projects — the highest-starred MCP servers, the most-shared `CLAUDE.md` templates — are overwhelmingly oriented toward increasing autonomy: memory, context engineering, hook automation, compaction. Comparatively little energy goes to audit tooling, drift detection, or anything whose purpose is to make supervision cheaper. The ecosystem has already voted, and the choice is autonomy. This is the environment in which provenance decays: not in spite of the human in the loop, but because the loop has been restructured into a shape that cannot detect the decay it was meant to prevent.

### Prior art and intervention

That decision lineage must be preserved as an artifact distinct from the code is not new. **Parnas (1994)** named software aging and prescribed design for change, which requires the original intent to be available and maintained. **Cunningham (1992)** named technical debt — but his metaphor was financial and intentional, debt taken on knowingly; provenance rot is its quieter cousin, decay no one agreed to. **Gall, Hajek & Jazayeri (1998)** and **Tornhill (2015)** built the coupling instrument that inverts cleanly into a decay signal. **Nygard (2011)** named Architectural Decision Records — the canonical prior-art answer, widely admired and inconsistently maintained, because maintenance is socially expensive and structurally optional. Each assumed the participant doing the work is a human who reads the documentation before changing the code — who internalises the ADR, remembers the design meeting, carries lineage between sessions. The agent does none of this. The ADR, if it exists, must be mechanically retrievable, explicitly linked to the code it describes, and trustworthy enough to act on without re-deriving it. The bar for the artifact rises substantially.

The intervention is to stop treating provenance as documentation and treat it as an event log: a structured record of intent events — created at session start, appended to as work progresses, sealed at completion, and attached to the commit that landed the change. Each event captures the what and the why — scope, rationale, assumptions in force, decisions made, alternatives rejected, what is out of scope — in a templated structure that forces the why field to exist. The log is queryable (the agent retrieves the intent that produced a piece of code before changing it), drift-detectable (an orphaned commit, or a sealed intent whose code was rewritten without a new intent, is the same Tornhill-inverted signal on structured artifacts), and auto-recorded by the agent's lifecycle rather than by social discipline. The maintenance ADRs require is replaced by lifecycle automation. The ADR was an artifact the team agreed to maintain; the intent log is one the system produces. Teams forget. Systems do not.

## Stakes: the regime, not a component

A user asks the agent to rename a config key, or delete a module, or change a signature. The agent complies — and warns about the migration path. It notes that consumers will break, suggests a deprecation shim, a version bump, preserves the old tests. None of this is wrong in general. All of it is wrong here, because the project is a four-week-old personal repository with no users, no integrators, no consumers but its author. The agent has protected stakeholders who do not exist.

This is a stakes failure, and it is unlike the others in this section. Provenance and horizon are content — things the agent does not know and must be told. Stakes is authority — how boldly the agent may act on what it knows, set by a balance of three forces: the external risk the work actually carries, the user's authority over it, and the agent's own. Caution is the delta between them. The whole-context section lifts stakes out of posture for exactly this reason — it is not a tense of the work but the regime the work is read under, the setting at which `GOAL = A(C)` is always evaluated.

The mechanism is precise. Caution is an actuarial calculation — how bad if this breaks, times how likely, against the cost of the safeguard — and to run it the agent needs a base rate: how exposed is this project, where authority sits. It is almost never told. So it falls back on the base rate implied by its training distribution — dominated by production systems with users, because production systems are what the world writes code and documentation about. Absent a declared regime, the agent assumes the modal one — over-weighting an external authority that is not there and under-weighting the authority it was actually granted. The failures fan out from that single imbalance: migration anxiety (caution for consumers that do not exist), ceremony inflation (branch-and-PR process for a solo project), stakeholder hallucination ("your users might expect…" about a project with no users), and stale-test preservation (old tests bent around rather than deleted, because the agent treats a verification surface as load-bearing when it encodes the architecture the change means to replace).

What stakes sets, in the end, is the definition of done. A greenfield regime calls a change done when it works; a production regime calls the same change done only when it is also migration-safe, backward-compatible, and shimmed. Get the regime wrong and done drifts out of reach — the agent piles on safeguards no one asked for, or declares completion against a bar that was never the project's. The agent is not being careful; it is being careful for the wrong project, against the wrong definition of finished. This is the least settled failure mode in this paper, named as an observation that warrants investigation rather than an established result: it is hard to point to a single instance where over-caution caused a clear, attributable harm — by construction the harm is a tax on velocity and a slow distortion of architecture, not a visible break. And unlike the entropies, stakes does not rise: it is set wrong from the first turn, or right from the first turn — a static miscalibration, not a decay. That is the last reason it is a regime and not a component: it does not accumulate, so there is no ledger to seal, only a dial to declare. Stakes must not be confused with the intent failures of the intent-gap section: over-caution rhymes with over-specification, but they are orthogonal. A task can be specified perfectly and still executed under the wrong stakes.

### Prior art and intervention

That a system's stakes should be declared rather than assumed is old news in two literatures. **Boehm (1981)** built project mode into COCOMO — effort and ceremony scale by whether a project is organic, semi-detached, or embedded — encoding one process does not fit all into the field's oldest quantitative model *(Boehm, B., 1981)*. **McConnell (2004)** made the craft version: appropriate process weight is a function of project size and stakes *(McConnell, S., 2004)*. The social sciences supplied the missing force — the audience. **Bell (1984)** named audience design: speakers style themselves to an imagined audience *(Bell, A., 1984)*; **Litt (2012)** and **Marwick & boyd (2011)** developed the imagined audience and context collapse, where invisible real audiences flatten into a single conservative default — an agent with no declared regime is the limit case, every project flattened into the modal one *(Litt, E., 2012; Marwick, A. & boyd, d., 2011)*; **Tversky & Kahneman (1974)** named anchoring, the drag toward an available reference point *(Tversky, A. & Kahneman, D., 1974)*; and **Vaughan (1996)** documented the opposite drift, normalisation of deviance *(Vaughan, D., 1996)* — establishing that stakes fails in both directions, so the point is not that more caution is better but that the regime must be declared, not drifted into. What that literature models is one of the three forces — the imagined external audience; the user's authority and the agent's own are the two it never had to name, because a situated human held all three at once. Every method assumed that participant — one who knows the stakes because they are in the project. The agent is situated nowhere, and acquires the regime only by guessing — anchored on a distribution that is not the project in front of it.

The intervention is a small, explicit declaration of the regime, read before the agent calculates caution: audience, maturity, reversibility, breaking-change tolerance, operational exposure, ceremony budget, velocity bias — and beneath them, where authority actually sits between user and agent. It does not make the agent braver or more cautious in general. It replaces an invented regime with a declared one — and because the regime is static, it is declared once and held: the slowest layer in the context, the one thing that does not move at the speed of the prompt. This artifact is proposed, not yet validated — its design space is open (whether a coarse maturity tag captures most of the value) and the experiments below are how to find out. What is defensible now is the diagnosis: an agent given no stakes assumes a regime, and the one it assumes is wrong in a consistent, measurable direction.

## Horizon: the future

A developer making a local change carries a rough picture of where the project is going, and that picture does two things at once. It quietly vetoes locally-reasonable choices that would make the future harder — a name that will collide with a planned concept, a boundary that will block an intended integration, a shortcut welded into the exact seam a future capability will need — and it quietly permits locally-unjustified ones the future will reward: the boundary drawn a little cleaner than today demands, the seam left where an intended capability will land. The agent carries no such picture. It optimises for the present request, and so it does both wrongs: it closes doors it does not know the project will need open, and it refuses to leave open the doors it cannot see a reason for — suppressing, as premature, the very investment the horizon would license. Horizon governs creation: it is the permission to keep a door open that a context-blind agent reads as YAGNI and declines.

The foreclosing case is a future-hostile decision: locally reasonable, globally costly, and invisible at the moment it is made because nothing in the current task reveals it. It surfaces only later, when the foreclosed path is needed and found welded shut. But the permission the horizon grants is exactly as dangerous when it is misread, and naming why is the core of this component. Future vision injected as instruction becomes premature implementation. An agent told the project will eventually support multiple backends will build the abstraction now, before it is needed, against the explicit wisdom of *You Aren't Gonna Need It*. So the permission carries a sharp boundary: keep the door open; do not walk through it. Supply the future at an authority low enough to shape which doors stay open — the cheap, option-preserving choice — without becoming a task to complete. Permission to leave a seam is not permission to build the room behind it.

The components differ in authority: comprehension is executable now, provenance is lineage to verify against, and horizon is direction only — non-executable unless explicitly promoted to intent.

### Prior art and intervention

Horizon's prior art is two traditions that look opposed. **Parnas (1972; 1979)** is the foundation: information hiding and designing for ease of extension and contraction are design for change — anticipate the changes a system is likely to face and hide each behind a boundary. Parnas's method presupposes the very artifact Horizon is meant to be: a statement of which changes to anticipate *(Parnas, D.L., 1972; 1979)*. **YAGNI** (Beck; Fowler) is the counter-pressure: do not build for an imagined future, because most never arrive and the speculative generality is pure cost *(Beck, K., 1999)*. **Baldwin & Clark (2000)** reconcile them in the language of real options: modularity has value precisely because it keeps options open without exercising them *(Baldwin, C.Y. & Clark, K.B., 2000)*. The reconciliation is the design constraint — keep the path open (Parnas) without building it (YAGNI), because an unexercised open path has value in itself (real options) — and it is only achievable if the future is held at advisory authority. Parnas's design for change assumed an architect who held the roadmap in their head and applied it tacitly; the anticipation was free because the future lived in the same mind writing the code. The agent holds no roadmap, and cannot acquire one except by being told — but being told, at full authority, makes it build the future today.

The intervention is a small, explicitly non-executable statement of direction: a north star, likely future capabilities marked not current scope, non-goals for now, design sensitivities, and promotion criteria that say what would turn a horizon item into actual intent. Each item carries volatility and a last-revalidated timestamp, so that a horizon not checked against reality grows weaker, not silently more authoritative — the inverse of how prose roadmaps rot. This component is the most forward-looking in the paper, and its instrument is the most speculative, for a reason worth stating plainly: a future-hostile decision can only be confirmed in hindsight, once the foreclosed path is actually needed. At the moment of the decision, the only thing to check against is a declared horizon — so the artifact is both the intervention and the measurement surface, and neither exists in deployed form yet. The diagnosis is sound; the instrument is a hypothesis.

## Completing the stance

The two tenses complete the posture: provenance (the past) and horizon (the future). Set against comprehension — the present — and read under the stakes regime, the architect's full carry is accounted for: what the work is, why the project is the way it is, where it is going, and how much any of it matters. The agent that holds none of it assumes all of it, toward the average of its training distribution. The accumulated miscalibration of provenance and horizon is the Entropy of Posture, and like the Entropy of Interaction it is meant to be measured, not merely asserted — its wake is read in the artifact's quality and in the transcript (the measurement section). A clean provenance log does not say where the project is going; a horizon does not preserve the reasoning behind existing code; and neither one declares the stakes — that is the regime's job, not the lineage's. Each is missing on its own terms; each must be supplied on its own terms.

## None of this is new

The prior art on stance is as old as the prior art on structure, and this section has cited it in place — Parnas, Boehm, Bell, Cunningham, Vaughan, Tversky & Kahneman, Baldwin & Clark, Nygard, Bainbridge, and Parasuraman & Riley, each decades old. What was missing was the participant who has to be told the stance because it carries none of its own. A human team remembered the conversation that produced each decision; a human developer knew the stakes because they were situated in the project; a human architect held the roadmap in their head. None of those participants is in the loop anymore. The stance they used to carry implicitly — past and direction, weighed by a settled sense of the stakes — has to become an artifact, because the participant that replaced them holds nothing between one prompt and the next.

---

The model did not get worse. The stance it has to assume got harder to supply. Provenance, horizon, and the stakes regime were never written down before, because the people deciding already knew them. Those people are no longer the ones deciding. The interventions in this section are not about constraining the model. They are about capturing the why the model cannot reconstruct, stating the direction it must see but must not build, and declaring the regime it would otherwise invent — so that remediation preserves lineage, today's choices stop foreclosing tomorrow's, and caution tracks the real project. Precision at the point the stance is set is cheaper than precision at the point the damage is found, and the difference compounds across every commit that inherits it.

## Experiments

**Decoupling drift in open-source repositories.** Across public repositories that use `CLAUDE.md` or equivalent convention files, measure the elapsed time and intervening commit count between an edit to the convention file and the next edit to any source file it textually references. The metric deliberately does not require detecting contradiction — only divergence in change frequency between coupled artifacts. The expected output is a long-tailed distribution where a few repositories maintain tight coupling and the majority exhibit unbounded drift.

**Fusion frequency under remediation.** Run a battery of remediation tasks on aged codebases under two configurations: (a) baseline — no provenance retrieval; (b) treatment — the agent first retrieves the intent-log entries for the affected files and must acknowledge the prior rationale before proposing changes. Measure net lines added, net symbols removed, and structural-metric movement (D′, CBO, cyclomatic). The hypothesis is that the baseline exhibits net-additive behaviour — fusion in operation — while the treatment removes more and degrades less, demonstrating that opacity is the mechanism, not capacity.

**Mechanical commit-vs-intent drift.** Given a codebase with an active intent log, classify each commit in a window as covered by a matching sealed event, covered by an event whose description no longer matches the change, or orphaned. The hypothesis is that the orphan rate is non-zero under any realistic workflow, and correlates with subsequent remediation cost on the same files — establishing the mechanical check as a leading indicator of where the next provenance collapse will occur.

**The modal-regime anchor.** Run a battery of identical refactor and breaking-change tasks under three framings: (a) declared personal greenfield with no users; (b) declared production system with consumers; (c) no regime declared. Score each on a caution profile — migration warnings, deprecation shims, tests preserved versus deleted, ceremony suggested, breaking changes refused. The two-part hypothesis: that (a) and (b) differ sharply and appropriately (the agent can calibrate when told), and that the undeclared (c) clusters near the production end rather than the midpoint (the conservative anchor). A confirmed (c)-with-(b) result is the core evidence that the regime is assumed toward the training distribution's mode.

**Regime declaration as caution control.** Across the same battery, supply a structured stakes declaration and measure whether the caution profile — and the agent's declared definition of done — moves to track it. The hypothesis is that a single coarse maturity tag captures most of the available correction, and that done shifts with it — telling the intervention's designers how minimal the artifact can be, which is the open design question the regime currently leaves unanswered.

**Horizon and premature implementation.** Author a horizon for a small project (a future capability, explicitly marked not-current-scope). Run present-scoped tasks under three conditions: (a) no horizon; (b) horizon at advisory authority; (c) horizon as ordinary instruction. Measure both the rate of decisions the horizon would flag as future-hostile and the rate of premature building (introducing the abstraction before any task required it). The hypothesis is that (b) reduces future-hostile decisions relative to (a) without the premature-implementation spike that (c) produces — the direct test of the low-authority design. The future-hostile measurement depends on a held-out "future" task set whose paths the early decisions can foreclose, the methodological cost of the component's hindsight-only nature.
