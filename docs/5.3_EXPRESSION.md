# 5.3 The Expression Gap

*The relationships an agent cannot see, cannot express, and cannot keep current, and why the cure is a better notation, not a bigger window.*

This is the third entropy, and the third component of the context: the counterpart to the Entropy of Comprehension (the intent-gap section) and the Entropy of Trajectory (the trajectory section), part of the `CONTEXT = COMPREHENSION + TRAJECTORY + EXPRESSION + AGENCY` the whole-context section defines. Where comprehension carries the intent and trajectory the lineage, expression carries the structure: the relationships of the work, compressed into a form the agent can read before it acts. Its failure shows up in what the agent builds, but the cure is something the agent is given, which is why it belongs in the context at all.

The complaints from the opening section that this section answers are the ones that survive every correction. You confirmed the agent understood the task. You watched it explain the plan back, coherently, and it was right. You approved each step. And the thing it built is still structurally indefensible: a module that swallowed responsibilities belonging elsewhere, a function written a second time fifty lines from the first, a boundary crossed so quietly no single diff shows it. None of this is a failure of understanding. The understanding was confirmed. It is a failure to give that understanding a shape, and it is the one entropy that fails even when the other two are held.

> The agent can hold the idea. It cannot hold the shape of the idea.
> The gap between what it understands and how it organises what it builds is the Entropy of Expression.

The parallel to the intent-gap section is exact. Comprehension is the gap between what was asked and what was interpreted; expression is the gap between what is understood and what is organised. Both are discontinuities between two things that should match, and in both the agent proceeds confidently across the gap because nothing in the loop renders it visible.

## Context Imprecision

A traditional agentic system gathers files, pulling each one in as though it changes as a whole and its relationship to the files around it were obvious or irrelevant. Neither is true. 

A source file is not an atom; it is a container of scoped items: classes, functions, enumerations, each with its own reasons to change, its own dependents, its own life. The agent is handed the container and left to infer the contents' relationships from a flat reading. The structure lives in the AST, and the AST is exactly what the interface discards. 

The same defect afflicts prose: a markdown document is gathered as a blob, and its main message can stay true while a paragraph inside it has gone stale. This staleness is not trivial, a single misleading paragraph is enough to pollute the model's understanding of a concept, derail a task, or overfit to superceded architecture. 

In both cases, the interface assigns equal weight to everything inside a boundary. In otherwords, it cannot tell the load-bearing chunk from the dead one. So the agent does the only thing the interface permits: it zeroes in on the region the task names. After all, this is the only scope it can hold without conflating concerns it cannot see at once. 

That focus is reasonable, and it is exactly how the damage starts. Code written for a later, higher-level goal is invisible from inside the local task, so the agent writes it again, slightly differently, under a different name. Over a long session, it has been observed anecdotally that most agents converge on a single scope (one file, one module) and shove every new item into it; presumably, since this is the only structure it can keep in view. 

The cost is more than bloat: it is the loss of a canonical source of truth. When one concept lives in three places, no decision can be made cleanly, because no one (agent or human) can say which copy counts. And the next model inherits the mess as the example of how this codebase is done, and extends it faithfully. The disorder becomes the convention.

## A Practical Example: Writing a Book

This problem is not specific to software. It appears anywhere a linear artifact must preserve complex, non-linear relationships.

A book is an obvious example. Early chapters written with an AI agent may appear coherent because the dependency graph is still small: characters, events, promises, constraints, and unresolved setups remain easy to hold. As the book grows, however, the prose remains linear while the structure becomes increasingly non-linear. A fact introduced in chapter two may constrain chapter twelve, even if it is never repeated in between.

The failure is not simply that the model “forgets.” The failure is that there is no reliable structural representation of what must remain true. The agent can continue producing locally fluent chapters after it has lost the global dependencies that make those chapters correct.

The safe solution is obvious but impractical: before writing each new chapter, the model would need to factually re-read every preceding chapter and reconstruct the active narrative state — what happened, what each character knows, what was promised, what remains unresolved, and what future writing must preserve.

The book example makes the flaw visible: the only safe continuation strategy is total prior-state reconstruction before every new step. That is neither reasonable nor scalable, which means the missing capability is not memory size, but structural expression.

## The Precision–Abstraction tension

To express a multidirectional relationship precisely seems to require context no window will reliably hold, which drives toward a tempting but wrong conclusion: 
> *the fix is for models to simply hold more, better, for longer.*

The escape is **abstraction**, and it works because precision and abstraction are not opposites. A good abstraction is selective precision: exact about what matters, silent about the rest. An entity-relationship diagram is simultaneously abstract and exact; a dependency graph states its edges precisely while discarding every line of implementation. 

An agent doesn't need the detail, only the skeleton. The corrective is a better representation, not a bigger context.

## Perfection Is Not the Point

This is where `D(x…) ≈ A(I)` earns its keep.

A simple diagram can carry relational information far more efficiently than prose. A pie chart does not need to be accompanied by a lengthy description of it's contents to be useful. Its value is that the model can infer structure from the image directly, using far less context than a prose description would require.

This is not a discovery of the agentic era. Venn diagrams, ERDs, UML, dependency graphs, and state machines exist because prose expresses relationships badly. Prose is linear; structure often is not. The model does not need a perfect map of the workspace. It needs a precise, abstract representation of the relationships that matter, kept accurate as the work changes.

Usual half-measures fail in opposite directions. A one-off Mermaid diagram has abstraction, but no durability. It may be correct when written, but once the schema, code, or architecture evolves, it becomes a liability. An artifact projected over these conditions does not express ownership, dependency, causality, or architectural significance.

A useful artifact is one that can provide well-known abstractions, while simultaneously providing structural and temporal precision. It must be maintained in delta against the evolving work, not frozen as a decorative snapshot or reduced to a flat list of names. This is compression in the sense the whole-context problem requires. The representation preserves structure while spending almost none of the window, where the same relationships in prose would overflow the context; the same files without relationships would fail to express the system.

Perfection is not the point. A representation can be incomplete and still be useful if it is accurate, consistent, and current. What matters is not whether the model sees everything, but whether it sees the right structure in a form it can reason over.

## The Existing Remedy

Because as the Entropy of Expression rises, the only remedy on offer is a larger and larger prompt: the user explaining the structure for the Nth time, or pointing the agent at a document gone quietly stale about some part of the project that evolved since. Each escalation is prose attempting to carry what prose cannot, and each collapses the advertised economy of the tool: the work the agent was supposed to absorb becomes the user's, re-narrated every session, or skipped, because the user cannot tell whether this session needs the setup, and the agent will not tell them. It is the same false remedy as "write better prompts," for the same reason: the notation that failed cannot be the notation that fixes it.

## The Proposed Solution

What the component needs is an artifact that can be examined cheaply, before the agent acts: a model of the workspace's relationships that answers the questions the agent currently answers by invention, what exists, what does not, how much of this should be built, and how it is likely to be used. It must be precise (resolved to the scoped item, not the file), abstract (a skeleton, not a transcript), and current (held in delta against the work, not frozen at the moment it was drawn). No tool we know of provides this, and the absence is why the most-offered remedy is the one that cannot work.
